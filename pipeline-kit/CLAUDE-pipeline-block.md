## Agent pipeline (orchestrator rules)

Feature work runs through four subagents defined in `.claude/agents/`: `po` → **owner approval** → `code` → `qa` + `reviewer` → merge to `{{STAGING_BRANCH}}` → **owner UAT on {{STAGING_BRANCH}}** → promotion to `{{PROD_BRANCH}}`. The main session is the orchestrator: it sequences, verifies, gates, and merges. It does not write app code itself. The owner touches the pipeline at exactly two gates — design approval and UAT. Diagram: `docs/architecture/agent-pipeline.md` (if you installed it; derived from this section; if they disagree, this section wins). Entry points (`.claude/commands/`): `/discover [theme] [count]` — research-only → ranked proposals, no build (one `po` call; proposals land in `claude/discovery-<date>.md`); `/feature` — kickoff, or `/feature #n` to build a discovery proposal (resumes that `po`); `/promote` — promotion from a fresh session; `/status` — ledger dashboard.

**Models and effort** (routing rule: `Gwin_Shared` repo, `instructions/06-model-routing.md`). Tiers map to models in one place: Standard = `claude-sonnet-5-5` (Sonnet 5.5), Advanced = `claude-opus-5-5` (Opus 5.5), Frontier = not set. `po` runs Advanced at high effort (ladder step 3; research and design judgment). `code`, `qa` and `reviewer` run Standard at medium effort (step 1) — `code` implements a tight spec, `qa` executes a test plan, and `reviewer` checks the diff cold against the approved design. Raise effort before you raise the tier. The full IDs pin the model version (the `opus`/`sonnet` aliases move to newer models over time); on Bedrock, Vertex or Foundry the IDs can differ, so use your provider's IDs. These are defaults: when a run needs more (for example a `reviewer` pass on an access-control or privacy change), the orchestrator may pass a stronger `model` on the Agent call for that one run; to change a default, edit the agent file's `model:` or `effort:` line.

**Sequence.** `po` produces the design doc (including its regression scenarios), mockups, and code prompt, then returns `READY_FOR_CODE: awaiting owner approval`. The orchestrator opens the mockups for the owner (paths under `{{MOCKUP_DIR}}/<feature>/`), summarizes the design in a few lines — always including the return trigger, the revenue lever, both metric hypotheses, the comparables `po` cited, and **the design doc's regression scenarios** (owner approval of the design is the approval of those scenarios; there is no separate scenario gate) — and lists any `DECISIONS_NEEDING_OWNER` with `po`'s recommendation. A `po` return with no `RETURN_TRIGGER`, a `REVENUE_LEVER` of `none` without a reason, no dated competitor citations, or mockups that look like a form goes back to `po` before the owner sees it. **Nothing goes to `code` until the owner says approve (GATE 1).** Change requests go back to the same `po` agent (resume it; don't start a fresh one). After approval, `code` implements and opens a PR against `{{STAGING_BRANCH}}`; `qa` and `reviewer` run on it independently — run both; `code` fixes what either blocks on, and the blocker re-runs (within the circuit breakers below).

**Verify artifacts, not claims.** A subagent's return is a report, not proof. Before merging, the orchestrator itself checks CI is green (`gh pr checks <n>` when `gh` is available; otherwise read `github.com/{{REPO}}/pull/<n>/checks` in a browser), the reviewer's verdict is visible on the PR (a `VERDICT: APPROVE` review comment, the default, or a GitHub approval the owner allowed at its prompt), and `qa/<n>/` contains the evidence the qa agent cited. "Passed" with no matching artifact is a fail.

**Merge gates — PR → `{{STAGING_BRANCH}}` (all required; autonomous, no owner click).** Design + mockups + regression scenarios owner-approved on record (via the design doc) · CI green · `reviewer` VERDICT: APPROVE · `qa` VERDICT: pass · `{{HANDOFF_FILE}}` rewritten in the PR and under the size ceiling ({{HANDOFF_MAX_LINES}} lines). The orchestrator never merges a PR it wrote code for; `code` never merges anything; `reviewer` cannot write. Separation of duties, enforced by role: `reviewer` returns a verdict, the orchestrator merges. Merge-to-`{{STAGING_BRANCH}}` is gated by this process.

**`.claude/settings.json` is advisory, not a control.** **`git` is allowlist-by-default.** There is no blanket `git:*` allow. A short list of named, subcommand-anchored safe forms runs quietly:
- `status`, `diff`, `log`, `show`, `add`, `commit`, `fetch` (except `--upload-pack`), `merge`, `rev-parse`, `rev-list`, `ls-files`, `diff-tree`, `cherry`, `blame`
- branch creation and switching: `checkout -b` (except `-f`/`--force`), `switch` (except `-f`/`--force`/`--discard-changes`/`-C`)
- branch listing: `branch` bare, `-r`, `-a`, `-v`, `-vv`, `--show-current`, `--list`
- reads: `config --get`/`--get-regexp`/`--list`, `remote [-v]`, `worktree list`, `stash list`

**Everything else prompts, because nothing allows it.** That covers every `git push` (it is also an explicit `ask`), so the pipeline's routine `git push origin claude/<branch>` prompts too. It also covers any global option before the verb (`git -P …`, `git -p …`, `git -c …`, `git -C …`, `git --no-pager …`, unless Claude Code's built-in read-only analysis already treats it as read-only), and any unlisted subcommand: `reset`, `clean`, `rebase`, `stash`, `restore`, `checkout <path>`/`checkout --`, `checkout <branch>`, `branch -d/-D/-m/-f`, `config` writes, `remote add`/`set-url`, `worktree add`, `mv`, `tag`, `update-ref`, `filter-branch`. Explicit `{{PROD_BRANCH}}`/force pushes are `deny`, and deny beats ask: ` {{PROD_BRANCH}}`, `:{{PROD_BRANCH}}`, `refs/heads/{{PROD_BRANCH}}`, quoted forms, `+…`, `--force`, `-f`, and `--mirror`/`--all` (which overwrite `{{PROD_BRANCH}}` without naming it). ` {{PROD_BRANCH}}*` also denies a push of any branch whose name merely starts with it (`maintenance-fix` when the branch is `main`); name feature branches `claude/<name>` and that never happens. A prefixed push like `git -p push origin HEAD:{{PROD_BRANCH}}` doesn't start with `git push`, so no deny catches it, but it still prompts. Expect a handful of prompts per feature: each push round, plus any off-list git command. That cost is accepted because neither a deny-list nor `git:*` can enumerate git's global options and refspec grammar. **A session started before `.claude/settings.json` changed does not apply the change — start a fresh session.** **Residual holes:**
- approval is human judgment on each prompt
- `gh` is allowlist-by-default too: only a read-and-PR subset runs quietly (`pr view/diff/checks/list/status/comment/review`, `pr create … --head <branch>`, `run view/list/watch`, `repo view`, `issue view/list`, bare `auth status`). Without `--head`, `gh pr create` can offer to push the current branch and so skip the `git push` prompt; that form is not allowed, and `code` pushes with `git push origin <branch>` first. `auth status --show-token`/`-t` is `ask`, and so are `pr comment --edit-last`/`--delete-last` and `pr review --approve`/`-a` (an approval can satisfy a required-review rule when the agent's identity isn't the PR author). Everything else prompts, and `gh pr merge`, `gh api`, repo admin (`repo edit/archive/rename/delete/sync`), `release`, `secret`, `variable`, `workflow`, `alias`, `extension` and `auth login/logout/refresh` are explicit `ask`. But an approved `gh alias set` or `gh extension install`, or an approved `gh api` call, can reach any admin action under a name no pattern sees (`gh alias set m 'pr merge'` then `gh m <n>` only hits the default prompt)
- project commands (npm/pnpm/yarn): the starter ships no rule for them, so every build, test, install or script run prompts. The installer may add a few exact lines (`npm run lint`, `yarn run test`, …) after detecting the tool, risk-scanning each script with its `pre`/`post` hooks and one level of what it calls, and showing the owner the exact list. That scan is best-effort: a deploy behind an unfamiliar command can slip past. More importantly, an allowed project command is effectively arbitrary code execution, like an approved `node`: `npm test`/`run lint`/`run build` also run test files, config files (vitest/eslint/next/tsconfig plugins) and build scripts, all of which Edit can change, so an allowed project command can reach `git push` or `gh` around the denies. Scripts that use task runners or workspace fan-out (turbo, nx, lerna, `npm-run-all`, `pnpm -r`, …) or name production credentials are never allowed. Nothing is allowed by wildcard, because yarn turns unknown verbs (`yarn ci`, `yarn ls`) into scripts or binaries and the tools differ on hooks. `install`/`ci` are never allowed: they run the project's own install scripts and every dependency's. Concrete publish/credential/run-any-package forms (`npm publish`/`exec`/`token`/`access`/`owner`, `pnpm publish`/`dlx`, `yarn publish`/`dlx`, `npx`/`pnpx`/`bunx`/`uvx`, `uv publish`, `pip install`, `cargo publish`, …) are explicit `ask`. bun, uv, poetry, pipenv, pdm, hatch, cargo and make projects get no project-command lines at all (their `run` executes any command)
- interpreters and fetchers (`node`, `python3`, `curl`, `wget`, `docker`, `make`) are `ask`. Once one is approved, its script can reach `git push`, `gh`, or the GitHub UI around any deny, and so can a browser extension you allow. Any MCP merge/push tools you add per the kit's SETUP.md are only as gated as the rules you write
- push denies match only the spellings listed: bundled short flags (`-uf`), abbreviated long options (`--forc`, `--mirr`, `--al`) and shell-split names (`m''ain`) fall through to the `git push` prompt
- **an allowlisted subcommand can still run a command through its options**:
  - `git fetch --upload-pack=<cmd>` (and its abbreviations) is an explicit `ask`
  - `--output=<file>` on `log`/`diff`/`show`/`diff-tree`/`stash list` can write any file, including `.git/hooks/*`, so it is an explicit `ask` (`git *--outp*`)
  - other transport, diff, and merge hooks need a config write, a hook file, or a binary on `PATH` (`git merge -s <x>` runs `git-merge-<x>`)
- **config and hook writes outside `git config`**: an `Edit`/`Write` (both allowed) to `.git/config` (`core.fsmonitor`, `core.pager`, `core.sshCommand`, `remote.origin.push`), to `.git/hooks/*`, or to `.claude/settings.json` itself may not prompt in a main checkout. After that, a quiet `git status`/`git commit` can run a command.
- all of these need the agent to deliberately issue an adversarial command; the patterns are advisory

Unless `{{PROD_BRANCH}}` has server-side branch protection, the real control on promotion to `{{PROD_BRANCH}}` is these orchestrator rules plus the owner gate. The `rm -rf`/`rm -fr`/`rm -r -f`/`rm -f -r`/`rm -Rf`/`rm -fR` spellings (Bash and PowerShell) are `deny`; another flag order, a path, or a script still gets past them. MCP connector rules only match the connector server ids they name.

**After the `{{STAGING_BRANCH}}` merge (UAT hand-off).** The orchestrator confirms the {{DEPLOY_HOST}} staging deployment for the merge commit is `READY`, writes a UAT checklist derived from the design doc's regression scenarios and the mockup states (one line each, with the staging URL for each screen), appends it to the feature's `{{HANDOFF_FILE}}` entry under `Awaiting owner UAT`, and returns to the owner with the staging URL + checklist. **Then it stops.** Nothing moves toward `{{PROD_BRANCH}}` without the owner. UAT happens on `{{STAGING_BRANCH}}`'s deployment, not the PR preview.

**UAT fail.** The owner's notes go to the same `code` agent (resume) as a fix PR against `{{STAGING_BRANCH}}`; `qa` + `reviewer` re-run; the orchestrator re-posts the UAT checklist. Loop until approved, within the UAT cap below.

**Promotion to `{{PROD_BRANCH}}` (GATE 2 — owner UAT approval is the go).** On "UAT approved" (or `/promote`), and only after production-verifying the previous promotion, the orchestrator opens the promotion PR `{{STAGING_BRANCH}} → {{PROD_BRANCH}}`, runs the same merge gates (CI green; a fresh-context `reviewer` on the promotion PR; no second `qa` unless the diff differs from what was UAT'd), merges, confirms the {{DEPLOY_HOST}} production deployment is `READY`, spot-checks {{SMOKE_URL}}, marks the backlog item shipped if the project tracks one, and prunes the feature's `{{HANDOFF_FILE}}` entry. Promotion is gated by the owner and enforced by these rules, not by a permission pattern — patterns can't see a PR's base branch.

**Owner-only actions (never delegated, never assumed).** Applying a production migration; deleting user data, branches, or files the session didn't create; any payment, purchase, or transfer; **promotion to `{{PROD_BRANCH}}` — no exceptions, not even docs-only**; anything a subagent returns as `blocked`. Prepare the action, state exactly what will happen, and wait for an explicit yes.

**Circuit breakers.** Autonomy without a budget is an open loop; these caps are conventions the orchestrator enforces (a `PreToolUse` hook counting `Agent` calls is the mechanical upgrade if they prove insufficient — not built).
1. **Fix loop: 2 attempts per PR.** `qa` fail or `reviewer` BLOCK → `code` fixes (resume same agent) → re-run the blocker. A second failure stops: `blocked` to the owner with the finding, both attempts' diffs, and `code`'s explanation. Never a third attempt without the owner. The breaker trips on an **event** — a failure while the counter is already at its cap — not on the value: `fix 2/2` after a second attempt that passed is fine and does not block merge or promotion. `fix` counts per PR, so a UAT fix PR (a new PR) starts at `fix 0/2`; `uat` and `agents` are per feature and never reset.
2. **Same failure twice = stop immediately.** If a re-run reproduces the *same* failing test, scenario, or finding after a fix, don't spend the second attempt — that's a misunderstanding, not a bug. Go to the owner.
3. **UAT loop: 2 cycles.** Two UAT fails on one feature → stop and ask whether to re-design (back to `po`) or drop it.
4. **`po` pre-check bounce: 1.** The orchestrator bounces a weak `po` return once; the second return goes to the owner as-is with the gaps listed.
5. **CI: one trigger per commit, no re-runs to "see if it passes".** A red run is read, not retried (shared test infrastructure has rate limits). A flaky-looking failure counts as a failure for rule 2.
6. **Per-agent effort cap.** Each agent file carries it: ~40 tool calls (~60 for `po` in Discovery mode, which is research-heavy), or ~3 attempts at the same sub-problem, without a reportable result → stop and return `blocked` with what was tried. Self-reported; a convention, not a hard limit.
7. **Feature-level agent budget: checkpoint every 10, hard stop at 30.** Every `Agent` call for one feature counts (po, code, qa, reviewer runs and resumes). At **10 and 20** the orchestrator checkpoints: it stops, reports to the owner what's done, what remains, and why it should continue, and waits for the owner's go. At **30** it hard-stops: it writes full state to `{{HANDOFF_FILE}}` and recommends continuing in a fresh session. That pauses the feature; it doesn't abandon it. The hard stop is there because context and token use are likely high by then. **Resuming past a hard stop (the one rule):** the ceiling rises only on the owner's explicit go. A bare "go" in chat raises it by **+30**, one more block (`agents 30/30` becomes `agents 30/60`). A `Budget: agents N` on a resumed `/feature <name>` sets it to exactly N, but only when N is greater than the current count; N ≤ count raises nothing, and the session only reports. Before the first `Agent` call, the orchestrator rewrites the ledger's denominator in `{{HANDOFF_FILE}}`. Without that go, the session only reports state. Counters themselves never reset. A hard stop halts `Agent` calls only. Orchestrator steps that need no agent may proceed. That covers a merge whose gates are already satisfied, a deploy `READY` check, the smoke check, marking the backlog item shipped, and pruning `{{HANDOFF_FILE}}`. A normal feature uses 5–6.
8. **Scope-growth stop.** If `code`'s PR touches more than ~2× the files the code prompt named, or adds a dependency, migration, or env var the prompt didn't, `reviewer` BLOCKs on scope and the orchestrator treats it as `blocked` to the owner, not a fix loop.
9. **Ledger.** Every feature entry in `{{HANDOFF_FILE}}` carries, directly under its heading, a state tag and one ledger line — `## <feature> — <State>` then `Loops: fix 0/2 · uat 0/2 · agents 1/30 · po-bounce 0/1` (seeded at kickoff with the first `po` run counted, so `agents` starts at 1; the denominator is the hard stop, 30 by default; `fix` is the current PR's count and resets per breaker 1). States: Designing · AwaitingDesignApproval · Building · InReview · OnStaging · AwaitingOwnerUAT · Promoting · Blocked. The orchestrator updates both on every transition; a fresh session reads them before doing anything, so the caps survive session boundaries. The ledger is durable only once the entry is committed, in a PR's `{{HANDOFF_FILE}}` or on `{{STAGING_BRANCH}}`. A session-ending stop before a PR exists is not durable: the orchestrator pastes the full `{{HANDOFF_FILE}}` entry into its chat return, and a fresh run that finds no entry re-seeds at `agents 1/30`. Finish to a PR within one session where possible.
10. **Blocked is terminal for the session.** A `blocked` return stops *all* agent work on that feature until the owner answers. No alternative route, no re-prompt, no fresh agent for a "second opinion."

Caps are fixed: fix 2, UAT 2, po-bounce 1, agents 30, with a checkpoint every 10. The owner may override the agents ceiling per feature run in the `/feature` kickoff. `Budget: agents N` writes the ledger as `agents x/N` and moves only the hard stop; the checkpoint cadence stays every 10. Agents never raise their own caps.

**Session naming.** Rename the session `{{PROJECT_NAME}} vNEXT/<feature>` as soon as `po` names the feature, then `{{PROJECT_NAME}} v<version>/PR#<n>/<feature>` when `code` returns the PR.

**Parallel features.** Additional `code` agents run in separate git worktrees (`isolation: worktree`), one feature per worktree, never two agents on one branch. Sequence their merges; merge `origin/{{PROD_BRANCH}}` into the branch (never rebase); never rewrite history on a shared branch.

**Context economy.** Subagent returns follow the fixed shape in each agent file; no narrative. Resume an existing agent for a fix-up rather than starting one that must re-read the repo. Grep/Glob first, read ranges, don't re-read after edits, batch independent calls.

**Project housekeeping.** {{HOUSEKEEPING_NOTE}}

**Session end.** Rewrite `{{HANDOFF_FILE}}` (open state only) before the orchestrator session ends, even when no PR shipped — the next session starts from that file.

**Stop conditions.** A `blocked` return from any agent stops the pipeline for that feature and goes to the owner. Don't route around it (circuit breaker 10). Batch `blocked` returns and owner decisions rather than asking one at a time.
